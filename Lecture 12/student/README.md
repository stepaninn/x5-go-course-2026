# Практика 12. Останавливаем обработчик файлов заказов

## Описание решения

Реализован сервис обработки файлов, который считает количество строк и слов в файле. Также написаны 3 теста: проверка вывода ошибки `waitLine()` при отмененном контексте, проверка корректной работы при большом бюджете и проверка отмени дочернего контекста при отмене родительского.

Решение проверялось следующими командами:

```bash
go run ./cmd/filecount
go test -run '^(TestWaitLineCancelWithZeroDuration|TestEnoughDeadline|TestCancelParent|TestEmptyInput)$' ./processor
go test -race -timeout 15s ./...
```

Каналы открываются и закрываются в `processor.go`. Горутина отправляет пути из `paths` в канал `jobs` и закрывает канал при выходе. Отдельная горутина через `wg.Wait()` ждет завершение горутины, которая отправляет пути из `paths` в канал `jobs` и горутины всех `workers`, которые обрабатывают файлы и кладут результат в канал `results`. После этого она закрывает каналы `results`, в через который передаются результаты обработки файлов, и `done`, который сигнализирует о завершении обработки.

Также при обработке файла в функции `waitLine()` создается канал с таймером из встроенной библиотеки `time`, который отправляет текущее время на свой канал, если время вышло.

Если вызвать `cancel()` и сразу после выйти из `main` без ожидания `<-done`, то вся программа завершится и обработчики могут не успеть увидеть сигнал, закрыть файлы и выйти.

## Описание задания

На прошлом занятии мы распределяли файлы между несколькими горутинами. Теперь оператор может отменить обработку, а на весь прогон есть общий лимит времени. Нужно передать этот сигнал до каждого работника и дождаться, пока все они закончат.

**Контекст** сообщает, что работа больше не нужна, и может задавать крайний срок. **Таймаут** — длительность ожидания, например 300 миллисекунд. **Дедлайн** — момент, когда этот срок закончится. В практике мы зададим один таймаут сразу для всех файлов.

## С чего начать

Откройте папку с этим README в IDE. Все команды выполняйте здесь, рядом с `go.mod`. Нужен Go 1.22 или новее. Внешние библиотеки и серверы не нужны.

```bash
go run ./cmd/filecount
go test -run '^(TestAnalyzeFile|TestProcessFiles|TestDuplicatesAndMissingFile|TestEmptyInput)$' ./processor
go test -timeout 15s ./...
```

Код уже распределяет задания, считает строки и слова и закрывает каналы после завершения. Обычный запуск выдаёт три результата, четыре теста из второй команды проходят. Полный набор пока сообщает об ошибках отмены: это и есть задача занятия. Тесты исходной заготовки заканчиваются примерно за две секунды. Параметр `-timeout 15s` защищает от зависаний, которые могут появиться во время работы над кодом.

## Что уже готово

В `processor/processor.go` функция `ProcessFiles` получает контекст, пути, число работников и задержку на строку. Она возвращает два канала:

- `results` передаёт результаты подсчёта. Без отмены для каждого входного пути приходит один результат, включая повторяющиеся пути и ошибки чтения.
- `done` закрывается после выхода раздатчика и всех работников. Закрытие этого канала означает, что они завершили работу. Сам вызов `cancel()` этого не гарантирует.

Раздатчик отправляет пути в `jobs`. Работники читают `jobs` и отправляют ответы в `results`. `sync.WaitGroup` уже учитывает и раздатчика, и работников. Отдельная горутина дожидается их, затем закрывает `results` и `done`. Сохраните этот порядок.

В `processor/file.go` готов подсчёт по строкам. `lineDelay` имитирует долгую проверку заказов в каждой строке. В обычном запуске задержка равна нулю. В учебном запуске можно поставить 200 миллисекунд.

В `cmd/filecount/main.go` уже читаются параметры запуска. Пока значение `-timeout` только печатается: в заготовке таймаут ещё не подключён.

## Что должно получиться

1. Один таймаут ограничивает весь прогон: ожидание заданий, обработку файлов и передачу результатов. Он начинается в `main`, перед вызовом обработчика. У каждого файла нет своего нового полного бюджета.
2. Контекст доходит через `ProcessFiles` и `analyzeFile` до `waitLine`. Сигнатуры и вызовы уже подготовлены; осталось использовать контекст в отмеченных местах.
3. Если контекст отменили заранее, обработчик не начинает файлы и не выдаёт результаты. Если отмена пришла в процессе, часть результатов может уже быть получена. Все запущенные функции должны выйти, а оба выходных канала — закрыться.
4. После отмены получатель может перестать читать `results` и ждать только `done`. Ни раздатчик, ни работник не должны застрять на отправке.
5. Отсутствующий файл даёт отдельный результат с ошибкой. Это не отменяет остальные файлы. Пустой список завершается без результатов. При `workers < 1` используется один работник.

При одновременной готовности результата и отмены `select` может выбрать любую готовую ветку. Поэтому мы не требуем точного числа частичных результатов после отмены. Для проверки причины используйте `ctx.Err()` и `errors.Is`.

## 30 минут в классе

**0–8 минут. Общий срок и отменяемая работа.** Откройте `cmd/filecount/main.go`, затем `processor/file.go`. Выполните `TODO 1`: создайте общий контекст с таймаутом, предусмотрите вызов `cancel`, проверяйте отмену перед открытием и между чтениями строк. Замените `Sleep` в `waitLine` ожиданием, которое может закончиться по сигналу отмены. Если контекст уже отменён, функция должна сразу вернуть его ошибку, в том числе при нулевой задержке.

```bash
go test -run '^TestWaitLineCanceled$' ./processor
go run ./cmd/filecount -timeout 120ms -line-delay 200ms
```

К восьмой минуте покажите, какой именно контекст приходит в `waitLine`. На этом шаге работа ещё может ждать отправки в канал: следующий шаг устраняет это ожидание.

**8–20 минут. Выход из ожиданий на каналах.** Откройте `processor/processor.go`. Выполните `TODO 2`. Найдите все места, где горутина может ждать другую горутину. Добавьте возможность закончить это ожидание по отмене. Проверьте случай закрытого `jobs` и не начинайте новый файл, если отмена уже известна. Сохраните владельцев каналов: `jobs` закрывает раздатчик, `results` и `done` — горутина после `wg.Wait()`.

```bash
go test -run '^(TestAlreadyCanceled|TestDeadlineDuringWork|TestCancelWithoutReading)$' -timeout 15s ./processor
```

К двадцатой минуте покажите, как выйдет работник, если он уже приготовил ответ, а получатель больше не читает `results`.

**20–30 минут. Проверка завершения.** Запустите все тесты. Откройте `TestCancelWithoutReading`: он получает первый ответ, отменяет обработку и ждёт `done`, больше не читая результаты. Объясните, почему закрытие `done` подтверждает выход всех работников и раздатчика. Затем сравните обычный запуск и запуск с таймаутом.

```bash
go test -race -timeout 15s ./...
go vet ./...
go run ./cmd/filecount
go run ./cmd/filecount -timeout 120ms -line-delay 200ms
```

В обычном запуске придут три результата: `orders-a.txt` — 3 строки и 5 слов, `orders-b.txt` — 2 строки и 4 слова, `empty.txt` — 0 и 0. Порядок произвольный. Причина завершения будет `<nil>`.

Во втором запуске должны появиться `context deadline exceeded` и сообщение о завершении всех работников. Он займёт примерно 120 мс, а не полную длительность обработки. Точное время зависит от планировщика. Пустой файл может успеть дать результат до отмены.

Для запуска с `-race` на macOS нужны cgo и компилятор C.

## Границы примера

Мы читаем небольшие обычные файлы из `testdata`. `os.Open` и `ReadString` сами не принимают контекст. Проверка между строками не умеет прервать уже заблокированный системный вызов. В этом примере отменяется искусственная задержка и ожидание каналов. Для сетевых операций используйте API с поддержкой контекста.

`runtime.NumGoroutine()` показывает общее число горутин процесса, включая посторонние. Разница «до и после» может помочь при наблюдении, но сама по себе не доказывает отсутствие утечки. В наших тестах сигнал `done` связан с `WaitGroup`, который учитывает все запущенные рабочие функции.

- Отменённый контекст при нулевой задержке: `waitLine` должен вернуть `context.Canceled`.

Запустите `go test -race -timeout 15s ./...` и `go vet ./...`. Все тесты должны пройти, детектор гонок не должен сообщать об ошибках. Сдайте код, тесты и короткий README с командами запуска. В README своими словами укажите, кто закрывает каждый канал и что произойдёт, если после `cancel()` сразу выйти из `main`.

Дополнительно, если осталось время: добавьте тест отмены родительского контекста при ещё не истёкшем таймауте потомка. Объясните, почему потомок не может продолжить работу до своего срока.

3. Где в программе создаётся общий бюджет? Что изменится, если создавать таймаут заново на каждый файл?
4. Какие три ожидания на каналах есть в обработчике? Как каждое заканчивается по отмене?
5. Что произойдёт с родителем, если отменить дочерний контекст? А с потомками при отмене родителя?

7. Почему одного счётчика `runtime.NumGoroutine()` недостаточно для нашего теста завершения?
