# Практика — Swagger для сервиса заказов

20 минут. Цель: открыть документированные операции в Swagger UI, выполнить запрос и сопоставить фактический ответ со спецификацией. Реализация HTTP уже готова.

## Стоп-точка 1 — первая спецификация, 6 минут

1. В `cmd/orders/main.go` добавить общие аннотации `@title`, `@version`, `@BasePath`. Базовый путь нашего API: `/api/v1`.
2. В `internal/httpapi/handlers.go` задокументировать `status`: краткое описание, тег, JSON-ответ `200` типа `StatusResponse`, путь и метод.
3. Выполнить `go generate ./...`.
4. Открыть `docs/swagger.json`: найти `swagger: "2.0"`, `basePath` и путь `/status`.

В `@Router` указать путь относительно `@BasePath`. Если повторить `/api/v1` в обоих местах, UI построит неверный адрес. Это генератор Swagger 2.0: название файла не означает OpenAPI 3.

Результат стоп-точки: генератор завершился без ошибки, операция присутствует в JSON.

## Стоп-точка 2 — документация в браузере, 6 минут

1. В `internal/httpapi/routes.go` подключить пакет `github.com/swaggo/http-swagger` и сгенерированный пакет `example.com/lesson9practice/docs`. Для `docs` нужен импорт ради выполнения `init`.
2. Зарегистрировать обработчик Swagger UI на `GET /swagger/`, настроив URL спецификации `/swagger/doc.json`. Вспомнить: обработчик UI реализует `http.Handler`, а не `http.HandlerFunc`.
3. Выполнить `go test ./...`, перезапустить сервер и открыть `http://127.0.0.1:8080/swagger/index.html`.
4. Через **Try it out** выполнить `GET /status`. Убедиться, что фактический адрес содержит `/api/v1` ровно один раз и сервер вернул `200` с JSON.

Результат стоп-точки: UI загрузил спецификацию и отправил настоящий запрос.

## Стоп-точка 3 — получение заказа, 8 минут

1. Задокументировать `getOrder`: `@Summary`, `@Tags`, `@Produce`, обязательный параметр `id` в пути, ответы и `@Router`.
2. Свериться с кодом: успешный ответ `200` содержит `OrderResponse`; ошибки `400`, `404`, `500` содержат `ErrorResponse`. `id` — положительное целое число.
3. Снова выполнить `go generate ./...`, перезапустить сервер и обновить UI.
4. Создать заказ запросом из `requests.http`. В UI получить созданный заказ по номеру, затем проверить номер `999` и нечисловой `id`.
5. Сравнить описание и фактический статус, `Content-Type`, поля ответа. Зелёная генерация сама по себе совпадение не доказывает.

Результат стоп-точки: `200` и `404` видны в UI, оба ответа соответствуют описанным типам.

## Если осталось время

Задокументировать `createOrder`: тело `CreateOrderRequest`, ответ `201` с `OrderResponse`, заголовок `Location`, ошибки `400`, `413`, `415`, `500`. Проверить пустое имя и нормальный запрос через UI. Теги `binding`, `minLength` и `example` помогают генератору, но HTTP-ввод по-прежнему проверяет Go-код.

## Перед завершением

Выполнить `go test ./...`. В результате должны быть изменённые аннотации, подключённый UI и три сгенерированных файла `docs`. Важнее уметь объяснить путь от комментария до реального HTTP-запроса, чем дописать все операции за отведённое время.
