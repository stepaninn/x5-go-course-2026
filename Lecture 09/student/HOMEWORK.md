# Домашняя работа — список заказов и его контракт

Продолжить этот же сервис заказов. Добавить `GET /api/v1/orders` с пагинацией и описать его в Swagger. Новый ресурс создавать не требуется.

## Поведение списка

Ответ `200` — JSON-массив заказов. Каждый элемент имеет ту же форму, что и `GET /api/v1/orders/{id}`. Сортировка всегда по `id` по возрастанию. Пустая выборка и страница за пределами списка возвращают `[]`, а не `null` и не `404`.

| Параметр | Правило |
|---|---|
| `limit` | Необязательный, по умолчанию `20`, допустимые значения `1..100` |
| `offset` | Необязательный, по умолчанию `0`, целое число `>= 0` |

При явном неверном значении вернуть `400` с `code: "INVALID_QUERY"`. Не заменять неверное значение значением по умолчанию. Проверить пустые значения, буквы, отрицательные числа, `limit=0`, `limit=101` и число, которое не помещается в `int`. Повторные и неизвестные query-параметры отвергать с тем же кодом ошибки. Десятичные цифры — единственный допустимый формат числа.

Пример после создания трёх заказов: запрос `?limit=1&offset=1` возвращает массив только со вторым заказом. Огромное допустимое значение `offset` должно вернуть пустую страницу без panic. Не вычислять непроверенную сумму `offset + limit`.

## Документация и проверки

1. Добавить swaggo-аннотации запроса, ограничений query-параметров, массива в `200` и ошибок `400`/`500`.
2. Проверить `basePath`, относительный путь `@Router`, имя DTO и тип ответа в сгенерированном `swagger.json`.
3. Убедиться, что все уже существующие операции также описаны и доступны в UI.
4. Добавить HTTP-тесты для пустого списка, нескольких страниц, неверных query-параметров и большого `offset`. Сохранить работу создания и чтения заказа.
5. Перед сдачей выполнить `go generate ./...`, `go test -race ./...`, `go vet ./...`, `go build ./...`.

Сдать ссылку на репозиторий с кодом, `go.mod`, `go.sum`, сгенерированными `docs` и README с командами запуска. Срок уточняет преподаватель.

## Дополнительно — фильтр

Добавить необязательный `status` со значениями `new` или `cancelled`. Сначала применить фильтр ко всем заказам, затем сортировку и пагинацию. Иное или пустое явное значение — `400 INVALID_QUERY`. Пока API создаёт только заказы `new`, фильтр `cancelled` закономерно возвращает `[]`. Описать это в контракте.

## Дополнительно — изменение статуса

Добавить `PATCH /api/v1/orders/{id}/status` с телом `{"status":"cancelled"}`. Разрешён только переход `new` в `cancelled`: успешный ответ `200` содержит обновлённый заказ, повторная отмена возвращает `409` с `code: "ORDER_ALREADY_CANCELLED"`. Неизвестный заказ — `404`, неверный идентификатор или тело — `400`. Описать все ответы и покрыть тестами переход и конфликт. Проверять и менять состояние нужно атомарно, чтобы два параллельных запроса не отменили заказ одновременно.
