# Практика занятия 4

Соберите сервис уведомлений. Здесь email и push только сохраняют сообщения в память. Писем, push-запросов и сетевых вызовов нет.

## Обязательная часть на занятии

1. Прочитайте однострочный контракт Notifier. Он уже дан, чтобы заготовка компилировалась. Объясните, зачем диспетчеру именно этот метод.
2. Реализуйте Send у *EmailNotifier и *PushNotifier. Добавляйте в Messages строку, полученную через n.Label(message). Возвращайте nil. Пример: канал email и текст Заказ готов дают `[email] Заказ готов`.
3. Реализуйте Dispatch: последовательный вызов каждого Send ровно один раз с неизменным сообщением. При первой ошибке сразу верните тот же объект ошибки; последующие каналы не вызывайте. Без ошибок верните nil. nil-слайс и пустой слайс допустимы.
4. Ошибки пока только передаём вызывающему коду. Возвращать error и сравнивать с nil разберём перед практикой. Создание и классификация ошибок будут на уроке 5.

В all передаются корректные ненулевые каналы. Проверка nil-элементов и typed nil внутри Dispatch не требуется. Пустой текст разрешён, формируется обычная строка с префиксом. Повторный Send дописывает сообщение, прошлые записи сохраняются. Разные экземпляры хранят отдельные истории.

## Продолжение и закрепление

5. Реализуйте EmailAddress через `email, ok := n.(*EmailNotifier)`. Для ненулевого email верните Address и true, даже если адрес пуст. Для другого типа, nil-интерфейса и nil-указателя верните "" и false.
6. Реализуйте Describe через type switch: `email: <Address>`, `push: <DeviceID>`, иначе `unknown`. nil и указатели nil тоже дают unknown. Dispatch при этом не должен проверять конкретные типы.
7. Добавьте compile-time проверки для *EmailNotifier и *PushNotifier.

Поля BaseNotifier, Address, DeviceID, Messages и сигнатуры функций сохраняйте: на них опираются тесты. Встраивание уже показано в заготовке; объясните, почему доступен e.Label. Самостоятельно можно сначала заменить его именованным полем, затем вернуть встраивание и сравнить вызовы.
