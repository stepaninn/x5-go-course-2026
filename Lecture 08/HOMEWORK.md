# Домашняя работа. Чтение заказа и проверка HTTP-контракта

1. Завершите практику: /health, POST /orders, chi, JSON access log.
2. Добавьте `GET /orders/{id}` через готовый store.ByID. Положительное целое число проверяется в обработчике. Нечисловой, нулевой, отрицательный или слишком большой для int ID: 400. Корректный отсутствующий ID: 404. Существующий заказ: 200 и JSON заказа.
3. Возвращайте `Location: /orders/<id>` при создании. Не принимайте id или status от клиента: сервер определяет их сам.
4. Через httptest проверьте health, создание, чтение созданного заказа, неизвестный заказ, неверный ID, пустое тело, сломанный JSON, неправильный тип customer и пустое имя. Проверяйте статус, Content-Type и важные поля тела.
5. Добавьте request_id в контекст, X-Request-ID в ответ и request_id в access log. У одного запроса должен быть один номер во всех связанных записях.
6. Добавьте recovery: если handler паникует до записи ответа, клиент получает 500 с общим JSON-сообщением, а access log содержит 500. Проверьте это тестом. Отдельный публичный panic-маршрут в итоговом приложении не нужен.

Дополнительные пункты: тело не больше 1024 байт с ответом 413; иной или отсутствующий Content-Type с ответом 415; запрет неизвестных полей; запрет второго JSON-значения после первого. После первого корректного объекта допускаются пробелы и конец потока. Эти требования относятся к нашим JSON-обработчикам. Формат автоматических 404/405 маршрутизатора проверяется отдельно и в этом задании не оценивается как ошибка JSON-helper.

Команды перед сдачей из этой папки:

```bash
go fmt ./...
go test ./...
go vet ./...
go build ./...
```

Не добавляйте в логи имена клиентов, тела запросов, пароли или токены.
