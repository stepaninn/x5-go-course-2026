# Практика. HTTP API заказов

25 минут. Продолжаем модель заказа: id, customer, status.

## 1. Проверка работы сервера, 7 минут

Реализуйте `GET /health`: статус 200, `Content-Type: application/json`, тело `{"status":"ok"}`. Запустите тест и сделайте запрос curl или Postman.

## 2. Создание заказа, 9 минут

Реализуйте `POST /orders`. Вход: `{"customer":"Анна"}`. На успехе верните 201 и объект с полями id, customer, status. Статус нового заказа: `new`. Для хранения используйте готовый `store.Create`.

Проверьте непустое имя после удаления пробелов по краям. Некорректный или пустой JSON и пустое имя должны давать 400 и JSON `{"error":"понятное сообщение"}`. При ошибке заказ не должен создаваться. Заголовок Content-Type в успешном и ошибочном ответе должен быть application/json.

Пример ручной проверки:

```bash
curl -i -X POST http://127.0.0.1:8080/orders \
  -H 'Content-Type: application/json' -d '{"customer":"Анна"}'
curl -i -X POST http://127.0.0.1:8080/orders \
  -H 'Content-Type: application/json' -d '{"customer":" "}'
```

## 3. chi и журналирование, 9 минут

Перенесите регистрацию тех же обработчиков на chi. Зависимость уже закреплена в go.mod. Добавьте middleware с JSON-логом через log/slog: method, path, status, duration_ms. Проверьте в журнале как успешный запрос, так и ошибку 400.

Если базовые обработчики ещё не готовы, сначала завершите их, а этот этап доделайте дома.

## Проверка результата

- Health отвечает 200, валидный заказ создаётся с 201.
- Ошибочный вход даёт 400 и не изменяет хранилище.
- Ответы собственных обработчиков содержат правильный Content-Type и корректный JSON.
- Повторное создание выдаёт другой ID.
- Тесты проходят; добавлены проверки POST, а не только готовый TestHealth.

Расширенные проверки тела, request_id и recovery описаны в домашней работе. Они не обязательны для завершения базового POST в первые 16 минут.
