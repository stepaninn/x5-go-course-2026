# Сервис заказов

Учебный сервис на Go для первого контроля. Позволяет создавать заказы, получать список и отдельный заказ, менять статус и просматривать историю

Данные хранятся в памяти, поэтому они удаляются после перезапуска приложения. Базы данных и авторизации пока что нет

## Запуск

Требуется Go 1.22 или новее

```bash
go mod download
go run ./cmd/api
```

Проверка доступности:

```bash
curl http://localhost:8080/health
```

Ответ:

```json
{"status":"ok"}
```

## API

| Метод | Путь | Назначение | Успешный код |
| --- | --- | --- | --- |
| GET | `/health` | Проверка доступности | 200 |
| POST | `/api/v1/orders` | Создание заказа | 201 |
| GET | `/api/v1/orders` | Список заказов по времени создания | 200 |
| GET | `/api/v1/orders/{id}` | Получение заказа | 200 |
| PATCH | `/api/v1/orders/{id}/status` | Изменение статуса | 200 |
| GET | `/api/v1/orders/{id}/history` | История статусов по времени изменения | 200 |

ID заказа является положительным целым числом и ставится сервером. Стоимость хранится целым числом в копейках

### Создание заказа

```bash
curl -i -X POST http://localhost:8080/api/v1/orders \
  -H 'Content-Type: application/json' \
  -d '{"items":[{"name":"Keyboard","quantity":2,"price":500000}]}'
```

В ответ приходит заказ с полями `id`, `items`, `total_price`, `status` и `created_at`. Для этого примера итоговая стоимость равна `1000000`, начальный статус `new`. История запрашивается отдельной ручкой

Правила валидации:

- список `items` не пустой
- название товара не пустое и не состоит только из пробелов
- `quantity` и `price` больше нуля
- итоговая стоимость вычисляется как сумма `quantity * price` для каждого товара и должна помещаться в `int64`

Обработчики создания и изменения статуса отклоняют некорректный JSON, неизвестные поля и несколько JSON-значений в одном теле запроса

### Получение заказов

```bash
curl http://localhost:8080/api/v1/orders
curl http://localhost:8080/api/v1/orders/1
```

Список возвращается массивом по времени создания, от ранних заказов к поздним. Если заказов нет, то в ответе пустой список

### Изменение статуса

```bash
curl -i -X PATCH http://localhost:8080/api/v1/orders/1/status \
  -H 'Content-Type: application/json' \
  -d '{"status":"processing"}'
```

Допустимы только переходы:

| Текущий статус | Новый статус |
| --- | --- |
| `new` | `processing` или `cancelled` |
| `processing` | `completed` или `cancelled` |

`completed` и `cancelled` - конечные статусы. Повторная установка текущего статуса также считается недопустимым переходом

При успешном изменении сервер возвращает обновлённый заказ и добавляет запись в историю. Первая запись истории появляется при создании

### История статусов

```bash
curl http://localhost:8080/api/v1/orders/1/history
```

Ответ - массив записей с полями `status` и `changed_at`, от ранних к поздним. Время создания заказа и изменений статуса записывается в UTC

## Ошибки

Ошибки обработчиков заказов возвращаются в JSON:

```json
{
  "error": "status transition is not allowed",
  "code": "INVALID_STATUS_TRANSITION"
}
```

| HTTP-код | Поле `code` | Причина |
|---|---|---|
| 400 | `INVALID_JSON` | Некорректное тело запроса |
| 400 | `INVALID_ID` | Некорректный идентификатор |
| 400 | `INVALID_ORDER` | Заказ не прошёл валидацию |
| 400 | `INVALID_STATUS` | Неизвестный или пустой статус |
| 404 | `ORDER_NOT_FOUND` | Заказ не найден |
| 409 | `INVALID_STATUS_TRANSITION` | Переход статуса запрещён |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка |

Подробности внутренних ошибок записываются только в лог, клиент их не видит

## Логирование и middleware

Логи выводятся в стандартный вывод в формате JSON через `log/slog`. Для каждого запроса записываются `method`, `path`, `status`, `duration`, `request_id` и признак прерванного запроса `aborted` (аналогично примеру кода из 8 лекции)

RequestID создаётся сервером, сохраняется в контексте запроса и возвращается в заголовке `X-Request-ID`. Счётчик уникален в пределах запуска приложения. Этот же ID добавляется в логи ошибок обработчиков

Recovery middleware перехватывает панику, записывает её в лог и возвращает безопасный JSON с кодом `500`. Если ответ уже начали отправлять, запрос прерывается: изменить отправленный статус уже нельзя. Сервер продолжает работу

## Swagger

После запуска приложения:

- [Swagger UI](http://localhost:8080/swagger/index.html)
- [JSON-спецификация](http://localhost:8080/swagger/doc.json)

После изменения аннотаций:

```bash
go generate ./...
```

Команда из `generate.go` запускает Swaggo и обновляет `docs/docs.go`, `docs/swagger.json` и `docs/swagger.yaml`. Версия генератора закреплена в `go.mod`, глобальная установка `swag` не нужна

## Структура проекта

| Путь | Назначение |
| --- | --- |
| `cmd/api/main.go` | Запуск сервера, настройка логгера и сборка зависимостей |
| `internal/order/` | Модель, интерфейс репозитория и предметные ошибки |
| `internal/repository/memory/` | Хранилище в памяти с mutex и глубоким копированием заказов |
| `internal/service/` | Бизнес-логика и модульные тесты |
| `internal/handler/` | Маршруты, HTTP-обработчики, работа с JSON и middleware |
| `docs/` | Сгенерированные файлы Swagger: `docs.go`, `swagger.json`, `swagger.yaml` |
| `generate.go` | Команда генерации документации |
| `tools.go` | Импорт генератора Swaggo для сохранения его зависимостей при `go mod tidy` |
| `go.mod`, `go.sum` | Версия Go и зависимости проекта |
| `Makefile` | Команды запуска, сборки, форматирования и проверок |

## Проверка

```bash
go test ./...
go test ./internal/service/... -cover
go vet ./...
go build ./...
```

Тесты сервиса используют `testing`, `testify` и тестовый репозиторий. Они проверяют создание и валидацию заказа, расчёт стоимости, получение заказа и списка, переходы статусов, добавление записей и порядок истории
